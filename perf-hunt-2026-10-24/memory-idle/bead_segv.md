Found while measuring idle memory (perf hunt image_plug-dru3): with jemalloc told to unmap freed memory (`MALLOC_CONF=background_thread:true,retain:false`), the server release segfaults within ~100 requests, every time (2 of 2 runs). Not a supported config, but it exposes a read outside a binary that can in principle also fault with the shipped jemalloc settings.

Crash: `erts_sched_2: segfault at 7f4ddced4fff ip 7f4df20725ef ... error 4` (read fault on the last byte of an unmapped page). With `+JPperf map`, the ip falls in `Image.Blurhash.Encoder.calculate_component/6` (+0xb7) in `image` 0.72.0 (deps/image/lib/image/blurhash/encoder.ex:24, matching `<<r::8, g::8, b::8, rest::binary>>` over pixel data that came from libvips). The faulting address is one byte before a page boundary, so the JIT'd match reads starting 1 byte BEFORE the binary's data. Vix hands libvips memory to Erlang as resource binaries (deps/vix/c_src/utils.c:218, `enif_make_resource_binary`), whose data is the raw g_malloc buffer; jemalloc large allocations are page-aligned, so the byte before can be on an unmapped page. ERTS-allocated binaries always have a header there, which is presumably why the JIT assumes the byte is readable.

With the default `retain:true`, jemalloc keeps freed address space mapped, so the preceding page is usually readable, but the first extent of a fresh jemalloc mapping placed after a hole could still fault; glibc's malloc puts a 16-byte header before every chunk, so it never faults there.

Repro: build the release, start with `MALLOC_CONF=background_thread:true,retain:false ELIXIR_ERL_OPTIONS="+JPperf map"`, send ~600 varied requests including `output=info,blurhash,lqip-css` at concurrency 4 over priv/static/images and test sources; `dmesg | grep segfault`, then find the ip in /tmp/perf-<pid>.map.

Next steps: reduce to a minimal OTP repro (a resource binary whose data starts at a page boundary after a PROT_NONE page, matched with `<<a::8, b::8, c::8, rest::binary>>`), check which OTP versions' JIT read before the binary start, and report upstream to OTP. Possible ImagePipe-side mitigation: copy libvips pixel buffers into ERTS binaries before bit-syntax matching (cost: one memcpy of the blurhash/lqip input, small after the thumbnail shrink).
